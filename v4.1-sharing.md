# v4.1 — Sharing on a network

*Steps 3–4 of `collaboration-plan.md`'s original v4.0. The tunnel is v4.2;
"Shared with me" is v4.3.*

## Context

v3.6 shipped the ops layer and v4.0 shipped live updates and the shared ghost, so
two clients on one board merge per node and see each other's edits as they land.
What is missing is what makes a second client possible for *someone else*: a link
you can hand a person, and a boundary that makes that link reach exactly one board.

These two land together and cannot be split. `collaboration-plan.md` states the
rule outright: **there must never exist a build where desktop binds `0.0.0.0` and
the gate isn't there** — that is a build where the café Wi-Fi has the whole library.

**Joining is browser-only in this release.** The guest opens the host's own page at
the host's own origin, so there is no guest-side database, no origin-prefix
refactor, and no CORS. Those are v4.3.

**Unchanged:** `lib/graph.ts` (no board-schema change), the `boards` and `settings`
tables (no migration), the `Op` union in `lib/sync.ts`, `lib/store.ts`,
`PUT /api/boards/[id]`, `lib/transfer.ts` and import/export, `lib/ai/*`. Still
exactly one unsolicited AI behavior and one user-invoked one — this release adds
no model call anywhere.

---

## 1. What makes a request `local` — the ruling this release turns on

`collaboration-plan.md` drafted `accessFor` as reading the peer address. **Next's
App Router does not expose the socket**, and the `Host` header is not a substitute:
a peer on the LAN can send `Host: localhost` and read naively that inverts the
strictest tier into the most permissive one — the same shape of mistake as the
`CF-Connecting-IP` trap, arriving a release earlier than expected.

So `local` stops being something a request *looks like* and becomes something it
must **prove**. The decision, in order:

```
1. CF-Connecting-IP / CF-Ray present  → never local, never trusted
2. x-smarti-local === SMARTI_LOCAL_SECRET (non-empty)  → 'local'
3. the server is not bound wide                        → 'local'
4. SMARTI_TRUST_LAN is set                             → 'trusted'
5. x-smarti-share resolves to this board               → { share: boardId }
6. otherwise                                           → 'denied'
```

**Rule 3 is what keeps the default install exactly what it was.** `npm run dev`,
`npm run start` and `./start.sh` all pin `-H ${SMARTI_HOST:-127.0.0.1}`, so on a
loopback-bound server nothing non-local can arrive at all — the operating system is
the boundary, and no header has to be believed to say so. A clone-and-run user sees
no change of any kind.

**Rule 4 is what keeps `--lan` exactly what it was**, bit-for-bit: that flag now
also exports `SMARTI_TRUST_LAN=1`, and a trusted caller reaches everything, as it
has since v2.5.

**Rule 2 is the only new proof, and it exists in exactly one place**: the desktop
app, which mints a per-run secret, hands it to the forked server as an env var, and
injects it as a request header into its own `BrowserWindow` session. The Electron
window can prove it is local. A machine on the LAN cannot guess a `randomUUID`, so
it gets the share tier at best.

**Rule 1 is v4.2's rule, landed now with its test.** `cloudflared` runs *on the
host* and dials loopback, so every tunneled request would otherwise arrive looking
local. It is cheaper to write the assertion while the file is being born than to
remember it under a feature. It fails safe: a local caller could forge those
headers, but that only downgrades access it already holds, while a remote caller
cannot strip them.

### The consequence, said plainly rather than papered over

**The gate only bites in one configuration — bound wide *without*
`SMARTI_TRUST_LAN` — and that is the desktop's new share mode.** On the web install
you cannot be reached at all without `--lan`, and `--lan` hands the network every
board and the provider key by design. So there the share token is a convenience
that puts a guest on the right board; it is not a boundary, and `start.sh`'s
existing warning block is already the correct words for it. The dialog says so too.
Pretending otherwise would be a security story that is not true.

## 2. `lib/access.ts` — new, a pure core and a bound wrapper

The split is `lib/ai/providers.ts` (pure, node-free, imported by the UI and the
tests) against `lib/ai/config.ts` (the one db-aware line), applied again:

```ts
export type Access = 'local' | 'trusted' | { share: string } | 'denied';

export function decideAccess(
  headers: Headers,
  boardId: string | null,
  env: AccessEnv,
  resolveToken: (token: string) => string | null,
): Access;

export function accessFor(req: Request, boardId?: string | null): Access;

export function canManage(a: Access): boolean;
export function canReachBoard(a: Access, id: string): boolean;
```

`decideAccess` is the whole decision above and takes every input as an argument, so
`access.test.ts` is a table of `Headers` objects and never touches `process.env` or
the hub. `accessFor` is the impure line: `process.env` and `boardForShare`.

**Refusals are `404` for anything board-scoped** — a stranger must not learn that a
board id exists — **and `403` for `/api/settings` and the library list**, where
there is nothing to conceal and a clear refusal is more useful than a lie.

## 3. `lib/hub.ts` — a second pinned map, not a field on `Room`

The registry is a sibling of `rooms`, pinned on `globalThis` for the identical
reason (`next dev` reloads a route module on edit, and a fresh `Map` there would
silently invalidate every live link).

**It must not live on `Room`.** `sweep()` deletes a room the moment
`subs.size === 0 && !lease`, so a token stored there would be revoked by the last
person closing a tab — a share that dies when the host looks away.

```ts
export function mintShare(boardId: string): string;
export function shareFor(boardId: string): string | null;
export function boardForShare(token: string): string | null;
export function revokeShare(boardId: string): void;
```

**Minting is idempotent per board**: reopening the dialog must not invalidate a
link you already sent. Tokens are `crypto.randomUUID()`, held in memory only, and
**die with the process** — v2.5's ruling that a network decision belongs to the
invocation rather than the install, applied to the capability as well. So closing
the app is the revocation story, a link is good for the session, and nothing is
persisted: no column, no table, no migration.

## 4. `lib/share.ts` — new, pure, node-free

```
http://<address>:<port>/board/<id>#s=<token>
```

**The existing page route, not a new `/b/`.** The shorthand buys nothing but a
second way to open one board.

**The token rides in the fragment on purpose:** a fragment is never sent to a
server, so the capability stays out of access logs, `Referer` headers and proxy
history. The page reads it and sends it as a header.

`shareUrl(origin, boardId, token)` and `parseShareToken(hash)` are the pure half.
`parseShareToken` is `parseBoard`'s doctrine in miniature — no fragment, a bare
`#`, junk, and a fragment carrying other keys all return null rather than throw.

Address enumeration is `node:os` and therefore stays in the route, not in this file.

## 5. `app/api/boards/[id]/share/route.ts` — new

`GET` (current state), `POST` (mint), `DELETE` (revoke), all `canManage` only — **a
guest can never mint a link to the board they were let into.** It returns every
non-internal IPv4 address the machine has rather than guessing one: `start.sh`
takes the *first*, which on a machine running Docker or a VPN is the wrong one, and
the person looking at the dialog knows which of their addresses is the real one.

`gated` rides in the response so the dialog can say, under `--lan`, that the token
is not the boundary there.

## 6. The gate, route by route

A helper call at the top of each handler, **not middleware** — Next middleware is
edge runtime and cannot see the hub.

| Route | Tier |
|---|---|
| `boards/route.ts` GET (incl. `?full=1`), POST | `canManage` |
| `boards/[id]/route.ts` GET | `canReachBoard` |
| `boards/[id]/route.ts` PUT / PATCH / DELETE | `canManage` |
| `boards/[id]/sync/route.ts` POST, GET (SSE) | `canReachBoard` |
| `boards/[id]/suggest/route.ts` POST | `canReachBoard` |
| `boards/[id]/ideas/route.ts` POST | `canReachBoard` |
| `settings/*` | `canManage` |
| `boards/[id]/share/route.ts` | `canManage` |

**The gate goes above the privacy check** in `suggest` and `ideas`, so a caller
with no right to the board cannot distinguish "privacy is on" from "no such board".

**A guest spends the host's provider key** — the ghost fires for the room and ⌘. is
live for them. That is correct (they are collaborating on the host's board, and the
lease means the room spends *less* than two tabs did before v4.0), and it belongs
in the Share dialog rather than in a provider bill. **Privacy Mode is the
guest-proof switch** and needs no change at all: it is already enforced server-side
against the stored board, so it also means "no guest spends my key here."

## 7. `lib/shareToken.ts` — the one DOM module

The mirror of `lib/download.ts`: the DOM line kept out of the pure module so that
stays testable, and untested by design because the logic is next door.

```ts
export function shareToken(): string | null;   // parseShareToken(location.hash), read once
export function isGuest(): boolean;
export function apiFetch(path: string, init?: RequestInit): Promise<Response>;
```

`apiFetch` adds `x-smarti-share` when a token exists and is otherwise `fetch`.
**Every client call site moves onto it** — the three in `useSync.ts`, the three in
`Board.tsx`, the one in `IdeasPanel.tsx`. Nothing in v4.1 forces that consolidation;
v4.3's origin prefix does, and doing it now makes that release one line inside
`apiFetch` instead of the same threading exercise repeated in three files.

**The token must be a module read, never a prop or a dep.** `handle()` in `useSync`
is memoized on `[boardId]` alone and the stream effect on `[boardId, loaded, handle]`
precisely so a keystroke cannot reopen the stream; a fresh `{ origin, token }` object
in a dependency array would undo that.

## 8. Guest mode — chrome that matches what the token reaches

A control you cannot use is worse than one that is not there; a control you cannot
*see* does not exist (v2.6). So `isGuest()` removes what a share token cannot
reach — the Home link, the ⌘K switcher, the ⚙ settings, Export — **and suppresses
their keyboard shortcuts in the same breath**, because a hidden control that still
fires on ⌘K is the reachability rule inverted.

What a guest keeps is everything that is the board: the name, Objective, Private,
Ideas, Find, Present, the Done bin, Center, undo and redo. Plus one quiet line
saying where they are: *shared board, hosted on `<host>`, live while that app is.*

`Board.tsx`'s `/api/settings` GET already falls back to defaults on failure — "no
row means the default stands" — so a guest's 403 there costs nothing and needed no
change. That is a seam cut in the right place three versions early.

## 9. `components/ShareDialog.tsx` — new

A `chrome-share` button beside Print and Export, the two other actions that take the
board out of the app. Local `useState` like `BoardSwitcher`, not a store flag:
sharing is session UI, not board content. **No keyboard shortcut** — the Export
button's own comment already records that the row is full.

The shell is `TemplateLibrary`'s verbatim: a `share-back` backdrop closing on
`onPointerDown`, an inner `role="dialog"` stopping propagation, a `share-head` with
a `share-x` titled `Close (Esc)`, and a window-level Escape listener. New `share-*`
classes in `app/globals.css` built from existing tokens only — **no new color
token, and nothing near the three-layer palette**: a share dialog is chrome, and the
board underneath it is unchanged.

Three sentences the dialog carries rather than the README, because they are true at
the moment you press the button: the link dies when this app closes, it reaches
this board and nothing else, and a guest spends your model provider key.

## 10. The desktop binds wide

`HOST` splits into `BIND_HOST = '0.0.0.0'` — the fork's `HOSTNAME`, and the
`freePort` probe, so a port free on loopback but taken on the wildcard is never
chosen — and `URL_HOST = '127.0.0.1'`, what the window loads and what
`waitForServer` polls.

**A listening server cannot rebind**, so widening on demand would mean a new port
and a window reload in the middle of a collaboration. The binding is therefore wide
from launch and the token is the boundary, which is the whole reason §1 needed a
proof of localness rather than a heuristic.

The proof itself is four lines: a `randomUUID` minted at boot, passed to the fork as
`SMARTI_LOCAL_SECRET`, and attached to every request the app's own window makes via
`session.webRequest.onBeforeSendHeaders`, scoped to the server's own origin.

**Written down because it is the one genuinely new exposure in this release:** the
desktop app now holds an open port on the LAN at every launch, where before it held
none, and will raise a firewall prompt on first launch on Windows and macOS. It is
gated — a caller without a token reaches nothing, not a board, not the library, not
the settings — but a gated port is not the same as no port, and that is a fact for
the README rather than a detail of the diff.

## 11. `start.sh` and `next.config.ts`

`start.sh` exports `SMARTI_TRUST_LAN=1` beside `SMARTI_HOST=0.0.0.0`, which is the
entire mechanism by which v2.5 survives this release intact. Its warning block is
already the right words and stays.

`next.config.ts` gains Tailscale's CGNAT range in `allowedDevOrigins`, without which
`next dev` over a tailnet serves a page that refuses its own API calls — the same
failure the RFC 1918 entries exist to prevent. It is **generated rather than
hand-listed**: 64 literal lines beside the existing 16 would be a wall nobody
re-reads, and the range is `100.64.0.0/10` expressed as arithmetic.

`npm test` (562 tests, 28 files), `npm run typecheck` and `npm run build` are green,
and the curl matrix above was run against three separate servers:

- **Bound wide with a secret** (the desktop's shape). A guest token reached that
  board's `GET`, its `sync` POST, its SSE `hello` and `/suggest`; and was refused —
  404 — on another board and on that board's `sync`. It was refused 403 on the
  library list, on `?full=1`, on `/api/settings`, on `/api/settings/test`, on `PUT`,
  `PATCH` and `DELETE`, and on minting a further share. No token and a stale token
  both 404. **A request carrying a valid local secret *plus* `CF-Connecting-IP` was
  refused**, which is the v4.2 assertion working a release early. The same matrix was
  then re-run against the machine's real LAN address, which is the only honest form
  of the test: 200 with the token, 404 without it, 403 on the library.
- **Bound wide with `SMARTI_TRUST_LAN=1`** (`./start.sh --lan`). Every route answered
  from the LAN address with no headers at all — v2.5 preserved bit-for-bit — and the
  dialog's `gated` flag came back false, which is what makes it say so.
- **Loopback, nothing set** (the clone-and-run default). Every route answered, the
  sync POST included, and the LAN address refused the connection outright. `.tables`
  reported `boards` and `settings` — **no new table**.

Minting is idempotent across GET/POST/POST/GET; revoking kills the link immediately
and a re-mint produces a different token, so the old link stays dead.

**And then it was done for real, which is the gate this release set itself.** The
desktop app hosting on one machine; a second device on the same network, and a browser,
opening the link as guests. The board came up on both and edits made on a guest appeared
live on the host — v3.6's merge, v4.0's stream and v4.1's gate working together across
real hardware rather than three servers on one laptop.

**It matters that this was the desktop and not `./start.sh --lan`.** The desktop binds
`0.0.0.0` with no `SMARTI_TRUST_LAN`, so that run went through the gate at its strictest:
the guests were admitted by the **token and nothing else** — under `--lan` they would
have been `trusted` on arrival and the link would only have been a shortcut to the right
board. So the boundary was load-bearing in the run that proved it.

It is also the half of §1 that curl cannot honestly test. A shell can always set
`x-smarti-local`, so the local secret only ever looks like a working proof against
forged headers; what it has to actually do is separate the app's own window from a
machine on the LAN. Here it did — the host kept its library, its settings and its Share
dialog while the guests reached one board — which is rule 2 of `decideAccess` confirmed
by two computers rather than by an assertion.

### What this document got wrong, corrected in the code

1. **`isGuest()` cannot be read during render.** The token lives in the URL fragment,
   which the server by definition never receives, so an inline read renders one thing
   on the server and another on the client and hydration disagrees. It is set in an
   effect instead, at the cost of one frame of host chrome on a guest's first paint.
   §8 described the behaviour correctly and the mechanism not at all.
2. **The keydown handler reads `isGuest()` at event time, not the state.** That
   effect runs with `[]` deps and reads the store through `getState()` for exactly
   this reason; closing over a `guest` variable would have captured `false` forever.
3. **`freePort` had to move to the bind host too.** §10 named the fork's `HOSTNAME`
   and the window's URL and missed the probe in between — a port free on loopback but
   taken on the wildcard would have been handed over and then failed to listen.
4. **`POST /share` refuses a board that does not exist.** Not in §5: without it a typo
   mints a live token for nothing, and the dialog shows a link that opens an empty
   board somebody could later be given that id.

One thing left deliberately as drafted: the share URL's port comes from the request
the dialog made, not from configuration. That is right rather than lazy — the dialog
is reached over the same server it is describing, so the port it was asked on is by
construction the port that answers.
