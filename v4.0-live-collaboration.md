# v4.0 — Live updates and the shared ghost

*Steps 1–2 of `collaboration-plan.md`'s v4.0. Steps 3–4 (the access gate and share
tier 1) become v4.1; the tunnel becomes v4.2; "Shared with me" becomes v4.3.*

## Context

v3.6 shipped the ops layer: `lib/sync.ts` (`diffBoards` / `applyOps`),
`POST /api/boards/[id]/sync`, and `components/canvas/useSync.ts`. The canvas now
autosaves **what changed** rather than the document, so two tabs on one board no
longer clobber each other. What it deliberately did *not* do is tell the second
tab anything: a teammate's edit lands in the database and sits there until you
reload. The README says so in words.

This release closes that gap. A second client on the same board **sees** the
first one's edits as they land, and — because two clients on one board would
otherwise fire two `/suggest` calls per change and spend the host's key twice —
the ghost becomes a room-wide object with a lease.

**Nothing here widens the network.** Reach is exactly what it is today: loopback,
or the LAN if the operator passed `--lan`, which already exposes every board and
the provider key. `collaboration-plan.md`'s rule — *"there must never exist a
build where desktop binds `0.0.0.0` and the gate isn't there"* — is about step 4,
which is not in this release. `lib/access.ts`, `lib/share.ts`, `ShareDialog`,
`desktop/main.js` and the CGNAT range are all v4.1 and are **not** touched here.

**Unchanged throughout:** `lib/graph.ts` (no board-schema change), the `boards`
and `settings` tables (no migration), the `Op` union in `lib/sync.ts`,
`PUT /api/boards/[id]`, `lib/transfer.ts` and import/export, `lib/ai/prompt.ts`.
Still exactly one unsolicited AI behavior and one user-invoked one — and after
this, *fewer* calls per change, not more.

## 1. `lib/hub.ts` — new, server-only, node-free

In-process pub/sub. `Map<boardId, Room>` pinned on `globalThis` so `next dev`'s
HMR does not orphan subscribers when a route module reloads — the same reason
`lib/db.ts` holds a module singleton. No broker: one process is already a given,
and it is the same assumption `sync/route.ts` already leans on for its merge.

```ts
type Frame =
  | { type: 'hello'; seq: number; board: Board }
  | { type: 'ops'; seq: number; clientId: string; ops: Op[] }
  | { type: 'ghost'; phase: 'proposed'; proposalId: string; draft: ProposalDraft }
  | { type: 'ghost'; phase: 'accepted' | 'dismissed'; proposalId: string; text: string }
  | { type: 'ghost'; phase: 'released' }
  | { type: 'ping' };

export function subscribe(boardId: string, send: (f: Frame) => void): () => void
export function publish(boardId: string, frame: Omit<Frame, 'seq'>): number
export function claimGhost(boardId, clientId, fingerprint, now): boolean
export function releaseGhost(boardId, clientId): void
export function roomCount(boardId: string): number   // for tests
```

`seq` is a per-room monotonic counter, session-only and never persisted. It is
ordering information for debugging and for a client to notice a gap; it is **not**
a revision clock — arrival order at one process is still the total order, which is
what keeps the board schema untouched.

**The ghost lease.** One holder per room, TTL 30s. `claimGhost` returns false if a
live lease exists. `releaseGhost` clears it and its timer. **A lease that expires
undelivered broadcasts `{ type: 'ghost', phase: 'released' }`** — that needs a real
`setTimeout` per lease (one per room, cleared on release), not a lazy check on the
next claim: the losers stamped the fingerprint before their POST, so they are
blocked by `no_material_change` and will never call again on their own. Without the
timer a dead winner deadlocks the room's ghost until the next edit.

`lib/hub.test.ts` — new. The hub uses only `Map`, `Set`, `globalThis` and timers,
so it tests directly (vitest `environment: 'node'`, `lib/**/*.test.ts`): subscribe
and receive, unsubscribe stops delivery, `seq` is monotonic per room and
independent across rooms, one claim wins and the rest lose, release lets the next
claim through, an expired lease publishes `released`.

## 2. `app/api/boards/[id]/sync/route.ts` — a GET, and two lines in the POST

**GET — SSE.** Same idiom as `app/api/boards/[id]/ideas/route.ts:86-96`: a
`ReadableStream`, a `send(frame)` closure guarded by an `open` flag, `req.signal`
abort plus `cancel()`, `content-type: text/event-stream; charset=utf-8` and
`cache-control: no-cache, no-transform`. Differences from the ideas route:

- It opens with `hello` carrying `loadBoard(id)` and the room's current `seq`, so
  **an offline client resyncs by reconnecting rather than replaying a log.**
- It **needs a heartbeat** the ideas route does not: that stream is bounded by one
  model call, this one is idle by design. A `ping` frame every ~25s, and it is also
  how a dead subscriber is noticed and dropped.
- Its lifetime is the subscription: `subscribe()` on start, the returned
  unsubscribe in `cancel()` and in the `finally`.

**POST.** Three changes, all small:

- After `saveBoard(board)`, `publish(id, { type: 'ops', clientId, ops: body.ops })`
  and return the assigned `seq`. **Broadcast the ops as received, not as applied** —
  every receiver runs them back through `applyOps`, which is total, so an op the
  server dropped is dropped identically everywhere. No second serialization path.
- `clientId` stops being ignored (`route.ts:64-66` predicted exactly this) and
  becomes the echo-suppression key.
- An optional `ghost?: { phase: 'accepted' | 'dismissed'; proposalId: string; text: string }`
  rides the same body and is published after the ops. **Folding it in here rather
  than giving it its own route is a correctness win, not a shortcut:** accepting a
  ghost *is* accompanied by ops, and one request means no client can ever see "the
  ghost is gone" before "the node arrived", or the reverse. The empty-batch
  short-circuit at `route.ts:52-54` must be restructured so a ghost-only body (a
  dismissal carries no ops) is still published while still not churning
  `updated_at`.

## 3. `lib/store.ts` — `applyRemote(ops, dirty)`

```ts
applyRemote: (ops: Op[], dirty: NodeId[]) => void
```

Four rules, each of which is a visible bug if missed:

1. **Another person's edit is never in your undo stack.** No `pushUndo`, no
   `redoStack: []`. It *does* bump `lastMutationAt` — the board says something
   different and the ghost may notice. This is the descendant of v1's rule that a
   ghost *appearing* is not undoable but accepting one is.
2. **Never clobber a node with unsaved local edits.** The textarea is controlled
   over `node.text` and commits per keystroke, so a remote `node.put` mid-burst
   yanks the card out from under the typist. **Drop remote `node.put` / `node.del`
   for any id in `dirty`** — the set the hook computes from
   `diffBoards(basis, board)`. LWW already decided ours wins; the skip retires
   itself when the save acks. One rule covering live streaming, reconnect, and the
   open textarea at once.
3. **Rebase both stacks.** `undoStack` and `redoStack` hold whole `Board`
   snapshots (`lib/store.ts:164,170`), so a stale one resurrects what a teammate
   deleted. Run the kept ops over every snapshot: `s.undoStack.map(b => applyOps(b, kept))`,
   same for `redoStack`. No new logic, and ⌘Z then only ever undoes *your* edits.
   Consequence to accept and to write down: ⌘Z can restore their wording of a card
   you both edited. That is LWW applied to history, and the alternative is the
   per-field merge engine this whole plan exists to not need.
4. **Prune what points at what is gone.** `selectedIds` filtered, `selectedEdgeId`
   cleared if its edge left, `expandedIds` filtered. Clear `proposal` if a remote
   `board.set` turns privacy **on** — and *not* via `dismissProposal`, because
   nobody turned that idea down (the same distinction `setPrivacy` at
   `lib/store.ts:411-418` already makes). Leave `rejectedByBoard` and
   `deletedEdgesByBoard` alone.

Guards: no-op if `s.boardId` has moved on, and no-op if `kept` is empty (so an
all-skipped batch does not bump `lastMutationAt`). `lastTextEditId` is deliberately
untouched — a teammate's edit must not end your typing burst.

Two small siblings, both needed by the shared ghost:

- `releaseRequest: () => set({ lastRequestedFingerprint: null })` — the mirror of
  `markRequested` for the `released` frame. Deliberately **not** `failRequest`,
  which also stamps `suggestFailedAt` and buys a 30s cooldown; a released lease is
  not a failure, and the room should retry on the next tick.
- `receiveProposal(draft, proposalId?)` — the room-wide id, so accept and dismiss
  can name the same ghost across clients. Optional, so every existing call site and
  every test still compiles.
- `remoteRetireProposal(proposalId, phase, text)` — clears `proposal` if the id
  matches; on `'dismissed'` it also records `text` in `rejectedByBoard`, because
  **one person's "not that" is the room's**.

`beginLoad` needs no change: it already clears both stacks, the proposal and the
selection per board.

## 4. `components/canvas/useSync.ts` — the SSE consumer moves in

The v3.6 lifecycle is untouched: the debounce, the monotonic `saveSeqRef`, the
saving/saved/error indicator, the `SAVE_RETRY_MS` self-heal, `flushUnsaved`,
`beginBoard`, `seedBasis`. What is added:

- **A stable `clientId`** for this tab, sent with the debounced POST *and* with
  `flushUnsaved` (which currently sends `{ ops }` only, `useSync.ts:95`).
- **The stream, read with `fetch` + a `ReadableStream` reader, not `EventSource`.**
  This is the same shape `components/IdeasPanel.tsx:56-109` already uses, and it is
  the choice that survives v4.1: a share token must ride in a header, and
  `EventSource` cannot set one — the alternative is the token in the query string,
  which is the one place `collaboration-plan.md` says it must never be. Manual
  reconnect with backoff, closed by the board-switch effect and on unmount.
  StrictMode's double-mount must not leave two streams open — a `cancelled` flag
  and an `AbortController`, like the load effect at `Board.tsx:300-328`.
- **`hello` is the reconnect rule, and it is the hardest merge here.** The host's
  changes since our last ack are `diffBoards(basisRef.current, hello.board)` —
  **not** `diffBoards(board, hello.board)`, which would compute ops that wipe our
  own unsaved work. Feed that through `applyRemote`, then set
  `basisRef.current = hello.board`. Our surviving edits now read as dirty against
  the new basis and ride the next debounce; an in-flight POST re-sends harmlessly,
  because the ops are idempotent. If the basis is still null the board has not
  loaded yet and the frame is ignored — the load effect's `seedBasis` is authoritative.
- **`ops` frames from another `clientId` do two things, and the second is easy to
  miss:** `applyRemote(ops, dirty)` for the board, **and `basisRef.current = applyOps(basis, ops)`**
  for the basis. Without the second, every remote change reads as local dirt and
  gets echoed straight back on the next tick. A node we skipped as dirty stays
  dirty against the new basis, which is exactly right: our version re-sends and
  wins.
- Own-`clientId` frames are dropped.

**Latency contract, stated in the code:** content travels at ~`AUTOSAVE_MS` (700ms).
A collaborator's drag lands when it settles, not per frame. Flushing at commit
boundaries (drag end, edit blur) is a deliberate later tuning, not part of this
release; there is still no per-frame traffic.

## 5. The shared ghost

`shouldRequest` permits one live ghost per board; N clients fire N times and spend
the host's key N times. The lease fixes it, and it is **not deferrable** — it is a
correctness requirement of step 1, not a feature beside it.

- **`app/api/boards/[id]/suggest/route.ts`** takes `clientId` and the client's
  `fingerprint` in the body and calls `claimGhost` before it resolves a provider or
  spends anything. A loser gets `{ proposal: null, reason: 'claimed' }` — a refusal
  ranked with the existing ones (`privacy`, `no_api_key`, `upstream_error`,
  `refusal`), not an error. The winner mints a room-wide `proposalId`, and on a
  non-null draft publishes `{ type: 'ghost', phase: 'proposed', proposalId, draft }`
  and releases the lease. A null draft releases it too.
- **The client needs almost no new branch for `'claimed'`.** `Board.tsx:385-399`
  already treats a null proposal with a reason that is not `upstream_error` as
  "nothing happened", and `markRequested` (fired at `Board.tsx:376`, *before* the
  POST, deliberately) has already stamped the fingerprint — so a loser goes quiet
  and waits for the winner's frame instead of re-firing each tick. One explicit
  branch and a comment, so nobody later "fixes" it into a `failRequest`.
- **The lifecycle frames exist because ops alone retire nobody's ghost.** If Alice
  accepts, the diff builds her node everywhere, but Bob's `proposal` lingers. So
  `onAccept` / `onDismiss` at `Board.tsx:906-907` also send the `ghost` field on the
  sync POST, and every other client runs `remoteRetireProposal`.
- **Placement is per-client and that is accepted.** `receiveProposal` runs
  `placeProposal` against the local `viewRectFor`, which reads `collapseMode` and
  `expandedIds` — install-level and session-level respectively. Two clients with
  different fold settings may place the same ghost a little differently. It is the
  same idea, in the same layer, with the same id; converging the coordinate would
  mean the server doing geometry, which it has never done.
- **The three-layer invariant is untouched.** A proposal is still never a node,
  still never persisted, and still one per board — now one per *room* rather than
  one per tab, which is strictly closer to the rule.

### Four things this document got wrong, corrected in the code

1. **`ghost` frames carry a `clientId`, and the winner drops its own echo.** As drafted
   the winner learned its proposal twice — once from the `/suggest` response, once from
   its own broadcast — and would have re-placed it.
2. **The server mints `proposalId` and `/suggest` returns it** alongside the proposal, so
   the winner names the same ghost the room does.
3. **A dismissal carries no ops, so it cannot ride the autosave effect.** `useSync` gained
   `queueGhostEvent`, which stashes the event and bumps a nonce that re-arms the send, so a
   ghost-only body goes out on its own. §2's "restructure the empty-batch short-circuit"
   was only the server half of that.
4. **`applyRemote` takes the board id.** §3's guard — *no-op if `s.boardId` has moved on* —
   needs to know which board the ops are for, so the signature is
   `applyRemote(boardId, ops, dirty)`.

One thing left deliberately as drafted: on ack the basis becomes the board as it stood
when the batch was built, so a remote frame that landed mid-flight is not in it. That is
benign rather than a stale basis — the teammate's change *is* in our board, so the next
diff re-derives it as one of our own ops and re-sends identical content. Idempotent, one
extra op, self-healing. The comment in `useSync.ts` says so, because the "fix" for it is
the bug.
