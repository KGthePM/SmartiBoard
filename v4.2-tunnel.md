## Context

v4.1 made a board shareable with a link, but only to somebody who could already
reach the machine — the same Wi-Fi, or a tailnet. This is the second tier: a
`cloudflared` quick tunnel, which gives the install a public
`https://<random>.trycloudflare.com` address that a phone on cellular can open.
No account, no login, no DNS, no config.

**A tunnel forwards bytes and holds nothing**, which is the whole reason one is
admitted here where a hosted service is not: lose Cloudflare and only *reach* is
lost. Nothing about the board leaves the host's SQLite file.

**The tunnel is per install; the token is per board.** `lib/tunnel.ts` never
hears about a board and `/api/tunnel` is install-scoped behind `guardManage`.
What keeps a guest to one board is `lib/access.ts`, exactly as it does on the
LAN — **a bare tunnel URL with no `#s=…` reaches nothing**.

**Unchanged:** `lib/graph.ts` (no board-schema change), the `boards` and
`settings` tables (no migration), the `Op` union in `lib/sync.ts`,
`lib/store.ts`, `lib/access.ts` (the `CF-Connecting-IP` rule shipped early, in
v4.1), `PUT /api/boards/[id]`, `lib/transfer.ts` and import/export, `lib/ai/*`.
No AI behavior, no new persisted state, never a token: still exactly one
unsolicited and one user-invoked.

---

## 1. `lib/tunnel.ts` — new, server-only

A sibling of `lib/hub.ts`: spawn `cloudflared`, parse the hostname off its
output, hold at most one tunnel per install, die with the process. Pinned on
`globalThis` for the reason the room map is — `next dev` reloads a route module
on edit, and a fresh handle there would orphan a live child process with no way
to reach it again. Unlike the hub it spawns, so it is **not** node-free; the two
halves worth testing (`parseTunnelUrl`, `resolveBinary`) are pure and take their
dependencies as arguments.

**Never fetch a binary at runtime.** `resolveBinary` looks in `SMARTI_CLOUDFLARED`
(an explicit path, and the seam a desktop build will hand its bundled copy
across), then `PATH`, then gives up. A filesystem look, not a spawn: the dialog
asks for state every time it opens, and running somebody else's executable with
`--version` to decide whether a button is greyed out is the wrong trade. Absent
→ the tier greys out with one sentence and **never a download prompt**.

**It dies with the process.** v2.5's ruling that a network decision belongs to
the invocation rather than the install, applied a third time — so there is no
setting, no column and no migration, and quitting is how a tunnel is closed.
`startTunnel` is idempotent like `mintShare`: a second press while one is running
hands back the running one, and a press while one is *starting* joins that
attempt rather than racing a second `cloudflared` onto the same port.

## 2. `app/api/tunnel/route.ts` — new

GET / POST / DELETE, all three behind `guardManage`. Install-scoped, not
board-scoped: the share route is per board because a token names a board, but a
tunnel names a port and the port carries the whole app.

`guardManage` already refuses every proxied request — rule 1 of `decideAccess`:
a caller carrying `CF-Connecting-IP` or `CF-Ray` is never `local` and never
`trusted` — which closes the recursion for free. **You cannot open a tunnel
through a tunnel**, and a guest cannot open one at all.

The port is learned from the request rather than configured, the same trick the
share route's `state()` uses: the server does not otherwise know which port it
was told to listen on, and the desktop assigns a fresh one each launch.

## 3. The stream does not survive a quick tunnel — the finding this release turns on

Measured, not assumed. A tunnel was opened onto a probe route emitting one SSE
frame every 1.5s:

| | loopback | through the tunnel |
|---|---|---|
| `text/event-stream` | frames 1.5s apart | **one burst at the end** |
| `text/plain` | 1.5s apart | **one burst at the end** |
| `x-accel-buffering: no`, 512B–8KB padding | — | one burst at the end |
| 40 frames over 60s | 1.5s apart | **nothing for 63s, then all of it** |
| a raw Node server, no Next involved | 1.5s apart | **one burst at the end** |
| 64KB per frame (~590KB total) | 1.5s apart | **one burst at the end** |

**A Cloudflare quick tunnel buffers a response body until it ends**, and nothing
on our side changes it: not the content-type, not padding, not compression, not
the HTTP version, not the size. It is their edge, not our code — the raw-server
row is what proves that.

The same rig measured the other half, which is what makes the fix possible: on a
warm connection a request that *ends* is delivered essentially at once — a
handler holding for 2000ms returned in **2.047s**, about 47ms of overhead.

**So the answer is not to make the stream survive, it is to stop needing one.**

## 4. `?since=` — the room as a long poll

`GET /api/boards/[id]/sync?since=<seq>` returns `{ frames: Frame[] }` the moment
the room says anything, or an empty array after `LONGPOLL_MS` (20s), which is
this transport's heartbeat and the client's cue to ask again.

**It is a second delivery, not a second feature.** The room, the `Frame` union
and `handle()` on the client are the stream's, unchanged — so a polling client
hears `ops`, `hello`, `ghost` and `ping` exactly as a streaming one does, and the
shared ghost needs no special case.

Two rules inside it, both learned the hard way:

- **The batch is flushed a tick after the first frame, not immediately.** One
  POST can publish two frames — the ops, then the ghost frame riding the same
  request — and v4.0's rule is that no client may see "the ghost is gone" before
  "the node arrived". Splitting them across two round trips would be exactly
  that, reintroduced by the transport.
- **The poll subscribes *before* it decides what to answer.** Joining first
  creates the room, so a frame published while we look lands in the log rather
  than between the check and the wait — and it leaves a room behind for the next
  poll to resume from. Without it a lone poller finds no room every time, is told
  `null`, and is answered with the whole board **on a loop**. That was a real
  spin, caught by holding a poll by hand against a board nobody had open.

## 5. `lib/hub.ts` — a log, and a grace

A stream is subscribed for as long as it is open. A poll is subscribed only
while it *waits*, and the gap between being answered and asking again is where
both of this release's hub changes live.

**`framesSince(boardId, seq)` and a capped log** (`LOG_MAX = 256`). The contract
is the difference between `[]` and `null`: nothing has happened, versus *I cannot
account for the gap* — and only the second owes the client a `hello`. Three ways
to get `null`, each a real case: no room, a `seq` ahead of ours (a client from a
previous process — the counter is session-only), or more than `LOG_MAX` frames
missed. **Losing the log is safe**, which is why it is a plain array: the `null`
path is the same whole-board resync the stream already performed on reconnect,
so the log is an optimization over a correct path rather than a mechanism.

**`ROOM_GRACE_MS = 60_000`**, and `sweep` now defers rather than deletes. A room
swept in the gap takes its log and its counter with it, so the next poll resyncs
the whole board and finds an empty room again — a full board per remote edit,
forever. Rejoining inside the grace cancels the countdown outright.

## 6. `components/canvas/useSync.ts` — the fallback

The stream is tried first and **the poll is what it falls back to when it turns
out not to be one**. Detected by silence rather than caught as an error: a
buffered stream opens, is accepted, and then delivers nothing for as long as it
stays open. `hello` lands the instant the route subscribes, so `STREAM_PROBE_MS`
(5s) of nothing at all means the bytes are being held somewhere.

The fallback is **per board and one-way**. Reconnecting into a stream already
proved buffered would spend 5s blind on every retry, and nothing about a tunnel
changes while a board is open. `POLL_MIN_MS` (250ms) floors an *empty* answer
only, so a server answering "nothing" instantly cannot be turned into a spin
while a real frame still reconnects at once.

**Loopback and the LAN keep the transport they shipped with**, because the probe
never fires there.

## 7. `components/ShareDialog.tsx` — the second tier

A separator rather than a panel, because it is the same share reached a second
way, and it reuses `.share-go`/`.share-stop`'s rule outright — the difference
between the tiers is what the words say, not what the buttons look like. No new
color token.

**Tier 2 appears only once tier 1 is live**: a public address carrying no token
is a link to a refusal, so it cannot precede the token. The public link is
composed **client-side** from an install-scoped origin and a board-scoped token
via the pure `shareUrl`, which is what keeps `/api/tunnel` from ever having to
hear about a board.

Three caveats ride the dialog rather than the README, because they are true at
the moment the button is pressed:

- **Cloudflare terminates TLS**, so the board's text passes through their edge in
  readable form. Nothing is blocked — it is their board, their call.
- **Quick tunnels are not a paid service**: the address can slow down or stop
  working, and that is Cloudflare's doing rather than a fault here.
- **The tunnel is open for the whole app, not just this board.** The link is what
  keeps a guest to this one.

A fourth line sits on the link itself rather than in that list, because it is
about the first thirty seconds rather than about the trade: **a new address takes
a few seconds to start resolving.** Measured — a fresh hostname answered `host`
and `dig` before it answered `getaddrinfo`, and the lookups made too early left a
negative cache that outlasted the wait. Telling the person to wait is cheaper
than letting them conclude the link is broken and mint another.

## 8. `next.config.ts`

`*.trycloudflare.com` joins `allowedDevOrigins`. Without it `next dev` behind a
tunnel serves the page and then refuses its own API calls — the identical failure
the private ranges exist to prevent. It is public space, unlike everything else
in that list, but the entry means nothing unless a tunnel *this install opened*
is running: the hostname is assigned per tunnel and points at this machine only.

## Verification

- `npm test` — 580 passing. `tunnel.test.ts` covers `parseTunnelUrl` (including
  the schemeless mention that precedes the banner, and a chunk that splits the
  hostname) and `resolveBinary` (the order, the Windows file name, the refusal to
  fall back from a wrong explicit path). `hub.test.ts` covers `framesSince`'s
  `[]`-versus-`null` contract, the log's ceiling, and the grace in both
  directions. **The spawn is never exercised** — it would make the suite depend
  on a binary, a network and Cloudflare's edge.
- `npm run typecheck`, `npm run build` — clean.
- **Through a live public tunnel**, the scoping matrix:
  `/api/boards`, `?full=1`, `/api/settings`, `/api/tunnel` GET and POST → **403**;
  the shared board with no token, a junk token, or another board's token → **404**;
  with the right token → **200**; `DELETE` with the right token → **403**.
- **Through the same tunnel**, liveness: a bootstrap poll returns the board; a
  quiet poll holds for exactly 20.03s and returns `[]`; an op posted by the host
  at t+3.0s arrived at the guest at **t+3.52s**.
- **The fallback end to end**, run as the client runs it: the stream opens,
  delivers nothing, the probe fires at 5s, the poll takes over with `hello`, and
  subsequent host edits arrive 0.1–0.7s after they were made.
- **Loopback is unchanged**, checked with the same harness: `hello` at once, an
  op 0.01s after it was posted, `ping` every 25s, and **the probe never fires**.
- **Idempotence and teardown**: two POSTs to `/api/tunnel` a moment apart return
  one hostname and leave one `cloudflared`; `DELETE` closes it; killing the
  server takes the child with it, which is `lib/tunnel.ts`'s exit hook.
- **Latency over a free quick tunnel is variable** — 0.13s at best, several
  seconds when the edge is cold, and a brand-new tunnel was slower still until it
  settled. That is the "not a paid service" caveat being literally true, not a
  fault in the delivery.

**Visual, and the operator's:** the two tiers reading as different in kind, the
tier-2 block in all three themes, and the honest final test — the link opened
from a phone on cellular, and the same hostname with `#s=…` removed reaching
nothing.
